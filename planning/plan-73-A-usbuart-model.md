## 1. Goal

- `usbuart` channel objects accept three new optional pin keys:
  - `"txEnable"`: an output, 1 while the channel sends a frame (from the start
    bit through the last stop bit), else 0.
  - `"suspend"` and `"suspendLow"`: the channel's own USB-suspend outputs, with
    the device keys' levels (0 and 1 while the link is up).
- The `usbuart` device accepts three new optional keys:
  - `"configured"`: an output, 0 while the USB link is up (CH340 ACT#).
  - `"rxInvert"`: an input read once at start. If it reads 1, every channel's
    RXD is read inverted, with a floating RXD reading idle (CH340 R232). Z on
    `rxInvert` reads 0, the pin's built-in pull-down.
  - `"auxSupply"`: a third supply domain, `{"power", "pins", "vcc"}`, in the
    shape of `usbSupply` (CP2108 VIOHD and the UART3 pins).
- `listing_check` prints a part's third domain as `|vccc=<min>-<max>,in=<inputMax>`
  right after `|vccb=`.
- `SerialDraft.swift` has a field for each new key, and `PartKindKeysTests` passes.
- `docs/parts-format.md` § `usbuart` documents the new keys, and also `usbSupply`,
  which no doc names today
  (`grep -c usbSupply docs/parts-format.md` → 0).

### Non-goals (explicit constraints)

- No part file changes in A; no golden line moves (`git diff --stat backend/tests/golden` empty).
- Every existing `usbuart` behavior is unchanged: RTS/DTR asserted, TXD idle 1,
  txLed/rxLed, reset, CTS flow control, the 9600 8N1 default.
- No USB-side modelling (enumeration, suspend events, HID vs CDC): the link is up
  for the whole run, as today.
- The configurable GPIO alternate functions (TX/RX toggle, RS-485, clock output) are
  mapped only where they are the chip's default function (CP2110, plan-73-C). No
  per-part configuration key.
- `"suspend"` / `"suspendLow"` stay single pin names at device level (no array form).

## 2. Current State

`serial_usbuart.c` (header comment, lines 1–21) plays the PC on the USB side.
`CHANNEL_KEYS` (line 33) names `txd rxd rts cts dtr dsr dcd ri txLed rxLed`, and
`KEYS` (line 36) names `channels reset suspend suspendLow usbSupply`.

- `drive_outputs` (line 99) drives RTS/DTR 0, TXD at the line level, txLed/rxLed

  gated by reset (`gated`, line 95): Z in reset, X when reset is X.
- `rx_tick` (line 193) and `rx_wake` (line 169) read RXD through `input` (line 87,

- `ub_load_device` (line 396) reads each channel's keys with `serial_optional_name`

- **The CH340 facts the new keys model** (`ch340.pdf` V3D):
  - p.5–6: TNOW "indicates that the CH340 is sending data from the serial port
    with a high level, and becomes low level after the transmission is
    completed"; R232 high means "the RXD pin input is automatically inverted";
    "The IR# and R232 pins are only checked once after power-on reset".
  - p.4: R232 has a built-in pull-down, and ACT# is the "USB configuration
    completion status output, active low".
- **The CP2105 suspend pins are per interface** (`cp2105.pdf` Rev 1.4):
  - p.7 Table 7: pin 1 `SUSPEND / RI_SCI` and pin 17 `SUSPEND / RI_ECI`, each "In

    not … defaults to active-low".
  - p.14: "By default, both communication interfaces on the CP2105 are configured
    for GPIO Mode".
- **The CP2108 has three supplies** (`cp2108-datasheet.pdf` Rev 1.3):
  - p.6: VDD 3.0–3.6 V, VREGIN 4.0–5.5 V, VIO 3.0 V–VDD, VIOHD 2.7–6.0 V.
  - p.13–14 Table 4.1: VIOHD is the "High Drive I/O Supply" of UART 3's

    not high-drive.
- **The CP2110 RS-485 pin is a transmit-active output by default** (`cp2110.pdf`
  Rev 1.3):
  - p.18 Table 14: GPIO.3 "RS-485 Transceiver Control", GPIO.4 TX Toggle,
    GPIO.5 RX Toggle, GPIO.1/2 RTS/CTS.
  - p.20: "The RS-485 mode of GPIO.3 is active-high by default".

## 3. Design Overview

Six small additions to one model and one kind loader, each behind its own test:

1. **`txEnable`** (channel): a new `CP_TXEN` slot in `CHANNEL_KEYS`.
   `drive_outputs` drives it `gated(s, serial_tx_busy(&ch->line.tx) ? LOGIC_1 : LOGIC_0)`.
   That is the txLed rule with the opposite polarity, so it changes at the same
   ticks.
2. **`suspend` / `suspendLow`** (channel): two more slots. `drive_outputs` drives
   them like the device keys (0 and 1, gated). The device keys stay, so a chip
   with one suspend pair (CP2102, CP2104, …) keeps using them.
3. **`configured`** (device): a pin slot in `UbDevice`/`UbPins`. `drive_outputs`
   drives it `gated(s, LOGIC_0)`.
4. **`rxInvert`** (device): a pin slot plus `LogicValue rx_invert` in `UbState`.
   - `ub_start` reads the pin once (`serial_level(..., LOGIC_0)`: Z reads 0) and
     never again. A pin change does not re-read it.
   - A new helper `rx_level(s, c)` gives the level the receiver sees, and
     `rx_wake` and `rx_tick` call it in place of `input(... CP_RXD)`:
     - while `rx_invert` is 0, it is `input(RXD)` as today (Z reads 1);
     - while it is 1, the pin is read with Z as 0 and then swapped 0↔1, so X
       stays X and a floating RXD reads idle (1).
     - This follows `ch340.pdf` p.5: with R232 high "an inverter is automatically
       inserted inside the RXD pin, which defaults to low level". The pin's pull
       turns to a pull-down, so the idle line is low at the pin and 1 after the
       inverter.
   - The receiver's idle level is 1 in both cases, so `restart_lines` (`line.rx.last
     = LOGIC_1`) stays as it is.
   - With R232 at X the start read gives X, and every RXD read is X.
5. **`auxSupply`** (device, kind loader): `serial.c` loads it with the same
   `load_usb_supply` body, generalised to take the key name, into
   `device->aux_supply`.
   - `bind_usb_supply` marks its pins as domain 2 (a third `power`/`other` array
     pair in `SerialBound`).
   - The domains block allocates 3 entries when `aux_supply` is set, with
     `domains[2].vcc = aux_supply->vcc`.
   - `auxSupply` without `usbSupply` is refused: `"auxSupply" needs "usbSupply"`.
     The domain order is fixed: I/O, USB, aux.
   - The same "is not a power pin" and "no power pin is left" checks apply.
6. **Listing**: `listing.c` prints `|vccc=` for `domain_count == 3`. The `vccb`
   condition becomes `domain_count >= 2`. No shipped part has three domains
   before plan-73-C, so the goldens do not move in A.

Correctness risk is low and local. The one behavior change on existing code is
the RXD read path (item 4). It is a no-op unless a device names `rxInvert`, and no
device does before C. The existing loopback and waveform cases of `usbuart_test`
are its regression check.

This plan changes behavior on purpose, so byte-identity is not its gate. A's gate is
that the goldens do not move (no shipped part changes) and the new test cases pass.

Rejected alternatives:

- **An array form for the device `suspend`/`suspendLow`** (CP2105's two pins). This
  would change a key's type in the loader and in the Part Editor field
  (`.pin` → `.pins`) for all 10 existing devices. Channel-level keys add without
  touching them.
- **Mapping TNOW to `txLed`.** txLed is active low (0 while sending), and TNOW is
  high while sending. Using txLed would draw the wrong level.
- **Putting CP2108's VIOHD in domain 0.** The voltage check would then hold UART3's
  pins to VIO's 3.0–3.6 V, which is wrong for the 5 V VIOHD use the high-drive port
  exists for (p.6: VIOHD to 6.0 V).
- **A general `"supplies"` list replacing `usbSupply`.** That rewrites the five
  existing devices' JSON for one new chip. `auxSupply` adds without touching them.
